외장하드에 사진을 복사해 두었고, 클라우드에도 파란 체크 표시가 나타납니다. 그래서 “백업은 끝났다”고 생각하기 쉽습니다. 하지만 원본을 잃어버린 뒤에야 백업 파일이 열리지 않거나, 필요한 폴더가 빠져 있거나, 복원할 계정과 비밀번호를 모른다는 사실을 알아차릴 수도 있습니다.

백업을 확인하는 가장 확실한 질문은 “파일이 복사됐는가?”가 아니라 **“원본을 사용할 수 없어도 이 복사본으로 필요한 작업을 다시 시작할 수 있는가?”**입니다. 이를 확인하기 위해 실제 파일을 지우거나 PC를 초기화할 필요는 없습니다. 시험용 폴더를 만들고, 독립된 위치에서 일부 파일을 복원한 다음 열어 보고, 필요한 경우 SHA-256 값까지 비교하는 실험을 하면 됩니다.

이 글에서 제안하는 15분 백업 검증 실험과 점검표는 공식 제품 기능을 활용해 구성한 독자적인 실습 절차입니다. 특정 운영체제가 자동으로 “15분이면 모든 백업이 검증된다”고 보장한다는 뜻은 아닙니다. 15분은 중요한 파일 몇 개를 표본으로 점검하는 시간 목표이며, 방대한 사진 보관함이나 시스템 전체를 복구할 수 있다는 보증은 아닙니다.

1. 백업 성공의 기준을 다섯 단계로 나누기

“백업 성공”은 하나의 동작이 아닙니다. 다음 다섯 가지를 구분해야 합니다.

단계확인할 질문통과 예시
① 존재백업 위치에 파일이 실제로 있는가?외장 드라이브에 파일 이름이 보임
② 접근원본 PC 없이도 파일을 읽을 수 있는가?백업 장치에서 파일을 열 수 있음
③ 내용원하는 내용이 온전히 들어 있는가?사진 전체 표시, 문서 마지막 페이지 확인
④ 일치복사본이 의도한 원본과 같은가?동일 파일의 SHA-256 값 일치
⑤ 복구필요한 위치에 다시 꺼내서 쓸 수 있는가?별도 복원 폴더에서 파일을 열고 편집 가능

파일 수가 같다고 ⑤까지 통과한 것은 아닙니다. 같은 파일 이름이라도 내용이 달라질 수 있고, 파일이 존재하더라도 암호화 키가 없으면 접근하지 못할 수 있습니다.

영국 국가사이버보안센터(NCSC)는 백업을 별도 장소에 보관하는 것에 더해 실제 복원 절차를 테스트하도록 권고합니다. Microsoft와 Apple도 각각 파일 기록(File History)과 Time Machine에서 파일을 이전 버전으로 복원하는 기능을 제공합니다.

공식 근거: NCSC — Tested backups and restoration, Microsoft — 파일 기록으로 백업 및 복원

2. 왜 ‘클라우드에 동기화됨’과 ‘독립 백업’은 다를까?

클라우드 동기화는 여러 장치에서 같은 파일을 편리하게 사용할 수 있도록 변경사항을 반영하는 기능입니다. 반면 복구용 백업은 원본이 삭제·변경·손상됐을 때 돌아갈 수 있는 독립적인 복사본을 확보하는 것이 핵심입니다.

예를 들어 OneDrive 동기화 폴더에서 파일을 삭제하면 클라우드와 다른 동기화 장치에서도 삭제가 반영될 수 있습니다. Microsoft는 이를 명시하면서, 필요한 경우 OneDrive 웹 휴지통이나 이전 버전을 이용해 복원하도록 안내합니다. 다만 휴지통과 버전 기록은 보존 기간 및 계정·관리자 정책의 제한을 받습니다.

세 가지 상황을 구분하세요

상황가장 먼저 해야 할 일착각하기 쉬운 점
OneDrive 폴더에 파일이 보임온라인 전용인지, 로컬 사본인지 확인아이콘 표시만으로 오프라인 복원 가능하다고 생각
다른 기기에서도 같은 파일이 보임삭제·수정이 양쪽에 전파되는지 정책 확인동기화를 완전히 독립된 백업으로 생각
별도 외장 SSD에도 복사함연결 해제 후 파일 열기와 복원 시험복사 종료 메시지만으로 무결성을 단정

중요: 이 글의 실험에서는 원본 파일을 삭제해 동기화 전파를 시험하지 않습니다. 원본·클라우드에서 동작을 테스트하려다 가족 사진이나 업무 문서를 실제로 잃을 수 있기 때문입니다. 복원 대상은 언제나 별도의 시험 폴더로 지정합니다.

공식 출처: Microsoft — OneDrive 파일 삭제의 동기화 범위, Microsoft — OneDrive 파일 및 버전 복구

3. 준비물: 15분 실험에 필요한 것은 세 가지

시험은 복잡할 필요가 없습니다. 원본 파일, 백업 사본, 별도 복원 폴더만 있으면 됩니다.

  • 원본: 문서·사진·PDF 등 중요한 파일 세 개 정도. 먼저 실제로 열 수 있는지 확인합니다.
  • 백업: 외장 SSD, USB 드라이브, File History, Time Machine 또는 클라우드의 기존 백업 위치.
  • 복원 폴더: 원본과 같은 폴더가 아닌, 예를 들어 바탕화면의 ‘복원_시험’ 폴더.

표본은 어떻게 고르나요?

세 파일을 모두 같은 유형으로 선택하지 마세요. 작은 텍스트 파일 1개, 사진이나 PDF 1개, 크기가 비교적 큰 실제 사용 파일 1개처럼 특성이 다른 항목을 선택하는 것이 좋습니다. 특정 프로그램에서만 열리는 파일이라면 해당 프로그램에서도 복원 테스트를 수행해야 합니다.

원본이 아직 없다면

메모장 또는 텍스트 편집기에서 내용이 짧은 파일을 하나 만들 수 있습니다. 예를 들어 다음 두 줄을 쓰고 이름을 backup-test.txt로 저장합니다.

백업 복원 테스트용 문서 오늘은 복원된 파일을 열고 확인할 예정입니다.

이 문서는 실험용으로만 사용하며, 중요한 실제 파일의 백업 상태까지 증명하지는 않습니다. 나중에는 사진·업무 문서 등 실제 파일도 별도로 검증해야 합니다.

안전 원칙: 실험 중 ‘원본 삭제’, ‘드라이브 포맷’, ‘백업 초기화’, ‘기존 파일 덮어쓰기’는 하지 않습니다. 테스트가 끝나고도 원본과 정식 백업은 그대로 유지합니다.

4. 독자 제작 실습: 15분 검증 시간표

이 시간표는 몇 개의 표본 파일만 테스트할 때의 진행 예시입니다. 파일 크기와 장치 속도에 따라 더 오래 걸릴 수 있습니다.

시간 목표활동확인할 결과
0~3분중요한 파일 3개와 백업 위치 선정원본·백업 경로 기록
3~6분백업 장치 또는 클라우드에서 파일 찾기세 파일이 실제 존재
6~9분원본과 다른 폴더로 복사 또는 복원안전한 복원 사본 생성
9~12분복원본 열고 내용 확인문서·사진·영상 정상
12~15분1개 파일의 SHA-256 비교, 결과 기록원본과 복원본 일치 여부

실험 전 체크

원본 파일과 백업 파일의 이름이 같아도 다른 버전일 수 있습니다. 이 경우 같은 시점의 데이터인지 확인하세요. 예를 들어 어제 백업한 문서와 오늘 수정한 원본을 비교한다면 SHA-256 값이 다른 것은 당연할 수 있습니다.

또한 파일을 복원하는 동안 다른 프로그램에서 원본을 편집하지 않는 편이 좋습니다. 비교 대상이 변하면 결과 해석이 어려워질 수 있습니다.

5. 1차 검증: 백업 저장소를 원본과 별도로 열기

외장 드라이브에 파일을 복사한 경우, 사용 중인 컴퓨터의 원본 폴더를 계속 바라보면서 백업했다고 착각할 수 있습니다.

외장 SSD·USB라면

  1. 원본과 백업이 서로 다른 드라이브 또는 폴더인지 확인합니다.
  2. 운영체제의 안전한 제거 기능을 이용해 외장 드라이브를 분리합니다.
  3. 가능하면 다른 포트 또는 다른 신뢰할 수 있는 컴퓨터에 다시 연결합니다.
  4. 외장 드라이브의 백업 폴더를 직접 탐색합니다.
  5. 시험 파일을 찾아 이름과 예상 날짜를 확인합니다.
  6. 가능하면 드라이브에서 파일을 바로 열어봅니다.

드라이브를 분리했다가 다시 연결하는 이유는 백업 파일이 내부 저장소에 남아 있는 다른 항목이 아닌지 구분하기 위해서입니다. 이 실험만으로 드라이브가 앞으로 고장 나지 않는다는 보장은 없습니다.

클라우드 백업이라면

  1. 실제 서비스 웹사이트 또는 공식 앱을 엽니다.
  2. 로그인된 계정이 맞는지 확인합니다.
  3. 필요한 파일이 클라우드에 있는지 확인합니다.
  4. 파일을 다운로드할 수 있는지 시험합니다.
  5. 파일을 원본과 다른 로컬 폴더에 저장합니다.
  6. 인터넷 연결 없이도 그 다운로드 파일을 열 수 있는지 확인합니다.

클라우드 폴더의 작은 파일 아이콘만 확인하는 것과 서비스에서 실제 파일을 다운로드해 여는 것은 서로 다른 수준의 점검입니다.

6. 2차 검증: 파일 이름이 아니라 실제 내용을 확인

파일이 열리더라도 원하는 내용이 온전한지 확인해야 합니다.

문서

  • 첫 페이지뿐 아니라 마지막 페이지가 있는지 확인합니다.
  • 표와 이미지가 포함된 페이지가 정상인지 확인합니다.
  • 필요한 경우 시험 복사본에 새 문장을 추가하고 다른 이름으로 저장할 수 있는지 확인합니다.
  • 원본 파일은 편집하지 않습니다.

사진

  • 미리보기 이미지가 아닌 실제 파일을 엽니다.
  • 확대해서 이미지 일부가 깨지거나 줄무늬로 보이지 않는지 확인합니다.
  • 촬영 날짜, 픽셀 크기 등 필요한 정보가 남아 있는지 살펴봅니다.
  • 중요한 사진 보관함이라면 파일 한 장이 아닌 여러 시기의 사진을 표본으로 선택합니다.

동영상

  • 재생 버튼을 누르는 것만으로 끝내지 않습니다.
  • 앞·중간·마지막 지점으로 이동해 재생해 봅니다.
  • 오디오가 필요한 동영상이라면 음성도 확인합니다.
  • 별도 코덱이 필요한 경우 다른 기기에서의 재생 가능 여부를 고려합니다.

압축파일

  • 압축을 풀 수 있는지 확인합니다.
  • 내부에 예상한 파일과 폴더가 있는지 비교합니다.
  • 암호화된 압축파일은 암호를 알고 있는지 확인해야 실제로 복원할 수 있습니다.

이 단계에서 실패하면 SHA-256 비교보다 먼저 원본과 백업의 품질을 의심해야 합니다. 원본 자체가 이미 깨져 있다면 해시가 일치하는 복사본도 똑같이 손상됐을 수 있기 때문입니다.

7. 3차 검증: Windows 11에서 SHA-256으로 사본 비교하기

SHA-256은 파일 내용으로부터 계산하는 해시 값입니다. Microsoft의 PowerShell 공식 문서는 Get-FileHash 명령으로 파일의 해시를 계산할 수 있고, 기본 알고리즘이 SHA256이라고 설명합니다.

동일한 방식으로 처리한 두 파일의 SHA-256 값이 같다면 두 파일의 바이트 내용이 같다는 매우 강한 근거가 됩니다. 그러나 해시 일치만으로 파일이 정상적으로 열리는지 또는 최신 버전인지까지 보장하지는 않습니다.

Windows에서 따라 하기

  1. 백업된 시험 파일을 바탕화면의 ‘복원_시험’ 폴더로 복사합니다.
  2. 시작 메뉴에서 PowerShell을 실행합니다. 관리자 권한은 일반 파일 해시 확인에 필요하지 않습니다.
  3. 원본 파일의 정확한 경로를 확인합니다.
  4. 아래 형식으로 원본 파일의 해시를 계산합니다.
Get-FileHash -LiteralPath "C:\Users\사용자이름\Documents\backup-test.txt" -Algorithm SHA256
  1. 복원된 파일의 경로를 넣어 똑같이 계산합니다.
Get-FileHash -LiteralPath "C:\Users\사용자이름\Desktop\복원_시험\backup-test.txt" -Algorithm SHA256
  1. 두 결과의 Hash 항목을 비교합니다.
  2. 같으면 ‘검증 시점에 내용 일치’로 기록합니다.
  3. 다르면 복사 시점·백업 버전·파일 손상·편집 여부를 조사합니다.

명령의 사용자이름과 폴더 경로는 예시입니다. 컴퓨터마다 실제 경로가 다르며, OneDrive로 바탕화면과 문서를 동기화한 경우 일반적인 사용자 폴더 경로와 다를 수 있습니다. PowerShell에서 파일을 드래그해 실제 경로를 확인하는 등 자신의 경로로 바꿔야 합니다.

결과가 다르면 재복사하면 되나요?

원본과 복사본이 정확히 같은 버전일 때에만 해시 일치를 기대할 수 있습니다. 백업 이후 원본을 편집했다면 값이 달라도 정상일 수 있습니다. 기존 백업 사본을 바로 덮어쓰지 말고 어느 시점의 어떤 버전인지 먼저 확인하세요.

공식 출처: Microsoft Learn — Get-FileHash

8. Mac에서 SHA-256 비교하기

Mac에서는 터미널의 shasum 명령으로 SHA-256 값을 확인할 수 있습니다. Microsoft의 macOS용 보안 제품 문서에서도 shasum -a 256을 이용한 해시 검증 예시를 공식적으로 제공합니다.

따라 하기

  1. Finder에서 원본 파일과 백업 복원본을 각각 찾습니다.
  2. 복원본은 원본과 다른 ‘복원_시험’ 폴더에 보관합니다.
  3. 응용 프로그램 → 유틸리티 → 터미널을 엽니다.
  4. 아래 명령을 입력하되 실제 파일 경로로 바꿉니다.
shasum -a 256 "$HOME/Documents/backup-test.txt"
  1. 복원본도 같은 방법으로 실행합니다.
shasum -a 256 "$HOME/Desktop/복원_시험/backup-test.txt"
  1. 화면에 표시된 해시 문자열을 비교합니다.
  2. 값이 같다면 일치로, 다르다면 미확인으로 표시하고 원인 확인을 진행합니다.

경로를 잘 모를 때

터미널에서 명령어와 공백을 입력한 다음 Finder의 파일을 터미널 창으로 드래그하면 경로를 입력하는 데 도움이 될 수 있습니다. 다만 명령 실행 전에 경로가 의도한 파일인지 반드시 확인하세요.

터미널에서 파일을 삭제하는 명령은 필요하지 않습니다. 해시 계산은 파일 내용을 읽어서 값을 출력하는 작업이며, 이 실험에서는 파일 자체를 변경하지 않습니다.

공식 출처: Microsoft Learn — macOS에서 shasum -a 256 사용

9. SHA-256 결과 해석표: 통과·보류·실패를 구별하기

관찰 결과해석다음 조치
원본·복원본 해시 같고 내용도 정상선택한 파일의 내용 일치 및 열기 확인다른 파일 형식도 추가 점검
해시는 같지만 두 파일 모두 열리지 않음동일한 손상 데이터일 수 있음정상 버전이나 원본 이력 찾기
해시가 다르고 원본을 최근 편집함백업 시점이 다를 수 있음버전 및 백업 날짜 비교
해시가 다르고 같은 버전이어야 함복사 오류 또는 다른 파일 가능성새 사본 보존한 채 경로·버전 검토
해시를 구할 수 없는 파일접근 권한·온라인 전용·잠금 가능성다운로드·권한·앱 상태 점검
일부 파일은 복원되지만 특정 파일만 실패선택적 백업 누락이나 손상 가능성해당 파일의 백업 설정 확인
샘플 3개 모두 정상표본 검증 통과전체 백업 검증 완료로 단정하지 않기

핵심 한계: SHA-256은 파일의 내용을 비교하는 강력한 수단이지만, 암호를 알고 있는지, 프로그램이 설치돼 있는지, 파일이 원하는 최신 버전인지, 폴더 전체가 백업됐는지는 해시만으로 알 수 없습니다.

원본과 복원본이 서로 다른 형식으로 변환된 파일이라면(예: HEIC를 JPEG로 내보내기) 내용의 일부 시각적 결과가 비슷해도 해시는 달라지는 것이 정상입니다. 형식 변환과 동일 바이트 복사를 혼동하지 마세요.

10. Windows 파일 기록(File History) 복원 시험하기

Windows 11의 **파일 기록(File History)**은 문서·사진·동영상 등 파일과 폴더의 이전 버전을 외장 드라이브나 네트워크 위치에 백업하고 복원할 수 있는 Windows 기능입니다.

시험 복원 방법

  1. 제어판 → 시스템 및 보안 → 파일 기록에서 파일 기록이 실제로 설정돼 있는지 확인합니다.
  2. 외장 백업 드라이브 또는 네트워크 위치를 사용할 수 있는지 확인합니다.
  3. 파일 탐색기에서 복원하려는 파일이 있던 폴더로 이동합니다.
  4. 해당 폴더를 마우스 오른쪽 버튼으로 클릭해 이전 버전 복원을 선택합니다.
  5. 백업 날짜와 파일 내용을 확인합니다.
  6. 복원 버튼의 추가 옵션에서 다른 위치에 복원할 수 있다면 안전한 시험 폴더를 지정합니다.
  7. 복원된 파일을 직접 열고 필요한 내용이 있는지 확인합니다.

중요한 주의: Microsoft는 기본 복원을 실행하면 현재 파일이나 폴더를 대체할 수 있으며 이를 취소할 수 없다고 경고합니다. 이번 실험에서는 반드시 다른 위치에 복원을 우선 검토하세요.

파일 기록을 사용한 적이 없거나 백업 대상 폴더에 포함되지 않은 파일은 이전 버전 목록에 없을 수 있습니다. 복원 목록이 비어 있다면 백업을 만들어 둔 적이 있는지부터 확인해야 합니다.

공식 출처: Microsoft — 파일 기록을 사용한 백업 및 복원

11. Mac Time Machine 백업 복원 시험하기

Mac의 Time Machine은 문서와 사진 등 파일을 백업하고 이전 시점의 항목을 복원할 수 있게 해줍니다. Apple은 파일 하나 또는 폴더를 찾아 복원하는 공식 절차를 제공합니다.

시험을 안전하게 설계하려면

  1. Time Machine 백업 디스크가 실제 연결되고 인식되는지 확인합니다.
  2. 중요한 원본 파일과 별도로 시험용 문서나 폴더를 만듭니다.
  3. 해당 시험 자료가 백업된 시점을 확인합니다.
  4. 원본 파일과 충돌하지 않도록 서로 다른 위치나 이름의 시험 항목을 대상으로 복원 절차를 설계합니다.
  5. Finder에서 복원할 항목이 있던 폴더를 열고 Time Machine을 탐색합니다.
  6. 날짜를 선택하고 파일의 해당 버전을 찾습니다.
  7. 실제 복원 버튼을 누르기 전에 복원이 원래 위치로 돌아간다는 점을 확인합니다.
  8. 원본과 충돌하지 않는 시험 대상에서만 복원을 수행하고 열기 테스트를 진행합니다.

Apple은 Time Machine으로 복원한 항목이 원래 저장된 위치로 돌아간다고 설명합니다. 따라서 중요한 현행 문서와 동일한 위치에 시험 복원을 하면 원본과 충돌할 수 있습니다. 이 글에서는 별도 시험용 항목을 사용하는 방식을 권장합니다.

네트워크 디스크 백업의 상태 확인

Apple은 Time Machine의 네트워크 백업 디스크에 대해 백업 검증 기능을 제공합니다. 메뉴 막대의 Time Machine 메뉴에서 Option 키를 누른 채 **백업 확인(Verify Backups)**을 선택할 수 있으며, 네트워크 백업은 주기적으로 자동 검증되기도 합니다.

다만 디스크 상태 확인과 실제 파일을 되살려 열어보는 작업은 동일하지 않습니다. 두 가지 점검을 함께 수행해야 실제 복구 가능성을 더 잘 판단할 수 있습니다.

공식 출처: Apple — Time Machine 파일 복원, Apple — Time Machine 백업 디스크 검증

12. 실패 유형 A: 파일은 있지만 암호·계정이 없어 열 수 없음

백업 데이터가 존재하는 것과 백업 데이터에 접근할 권한을 확보하는 것은 다릅니다.

실험에서 확인할 것

  • 외장 드라이브가 암호화돼 있다면 복구 키나 암호를 안전하게 보관하고 있는가?
  • 클라우드 계정에 접근할 때 필요한 인증 수단이 하나뿐이지 않은가?
  • 중요한 문서가 특정 프로그램의 라이선스나 파일 형식을 요구하는가?
  • 기기 분실 후에도 외부 저장소와 백업 기록의 위치를 찾을 수 있는가?
  • 회사 자료라면 계정 퇴사·권한 변경 뒤 누가 복원을 승인할 수 있는가?

암호를 기록할 때의 위험

암호나 복구 키를 파일과 같은 드라이브에 평문으로 보관하지 않는 편이 안전합니다. 또한 이메일이나 공개 문서에 복구 키를 그대로 남기지 마세요.

이 실험의 기록표에는 실제 암호 대신 어디에서 안전하게 확인할 수 있는지만 적습니다. 복구 시험을 하려고 다른 사람의 로그인 인증 정보를 빌리거나 보안 정책을 우회해서도 안 됩니다.

13. 실패 유형 B: 백업은 있는데 가장 중요한 폴더가 빠져 있음

파일 세 개를 복원했다고 모든 문서와 사진이 보호됐다고 할 수 없습니다. 백업 프로그램마다 기본적으로 포함되는 폴더와 제외되는 폴더가 다를 수 있습니다.

‘놓친 폴더’ 찾기 질문

  • 작업 중인 디자인·영상 편집 프로젝트는 어디에 저장되는가?
  • 사진 원본이 다운로드 폴더나 별도 외장 디스크에도 있는가?
  • 게임 세이브, 프로그램 설정, 회계 파일은 사용자 문서 밖에 있는가?
  • 메일 보관 파일이나 암호화된 자료가 별도 폴더에 저장돼 있는가?
  • 대용량 파일이 자동 백업에서 제외된 적이 있는가?
  • OneDrive 온라인 전용 파일이 Mac·Windows의 백업 방식에서 실제로 포함됐는가?

Microsoft의 파일 기록은 라이브러리에 포함된 파일과 폴더 중심으로 백업되며 사용자가 라이브러리를 추가할 수 있다고 안내합니다. Apple도 Time Machine에서 제외된 항목이나 클라우드 동기화가 끝나지 않은 파일 때문에 백업이 완전하지 않을 수 있음을 설명합니다.

따라서 백업 프로그램 화면에 ‘성공’이 보이더라도 중요한 폴더가 백업 대상에 포함돼 있는지 별도로 확인해야 합니다.

공식 출처: Microsoft — 파일 기록에 포함되는 폴더, Apple — Time Machine 백업 실패 및 클라우드 동기화

14. 실패 유형 C: 원본과 백업이 동시에 삭제되거나 손상됨

같은 PC와 항상 연결된 외장 드라이브에 복사본을 한 개만 남겨두면, 물리적인 침수·화재 또는 악성코드 등에 의해 원본과 백업이 동시에 영향을 받을 수 있습니다.

영국 NCSC는 중요한 데이터에 대해 3-2-1 원칙을 소개합니다. 적어도 세 개의 사본을 두 종류의 장치 또는 매체에 보관하고, 그중 하나를 별도 장소에 두는 방식입니다. 또한 백업을 정기적으로 테스트하고, 랜섬웨어 등으로부터 격리할 방법을 고려하라고 권고합니다.

예시 구성

역할예시 장소장점주의사항
원본 1개현재 작업하는 PC즉시 편집 가능PC 손상 시 영향
추가 사본 1개외장 SSD별도로 파일 접근 가능연결 상태 유지 시 공격·사고 위험
추가 사본 1개다른 장소의 안전한 백업한 장소 사고 대비계정·암호·접근권 관리 필요

이는 한 가지 가능한 설계 예시이지 반드시 유료 클라우드를 써야 한다는 뜻이 아닙니다. 외장 디스크 두 개를 번갈아 보관하거나, 별도 장소에 백업을 두는 등 상황에 맞게 설계할 수 있습니다.

동기화와 오프라인 백업을 구분하세요. 클라우드 동기화만 사용하는 경우 실수로 삭제된 파일이 다른 장치에도 반영될 수 있습니다. 실제 복원 가능한 버전이 남는지 시험하고, 핵심 자료는 독립된 복사본을 보관하는 편이 좋습니다.

15. 점수표: ‘백업됨’이 아니라 ‘복원 준비됨’ 판정하기

이 점수표는 이 글에서 독자 편의를 위해 제안한 자체 체크 방식이며 국가기관의 공식 인증이나 보안 수준 평가가 아닙니다. 체크 항목마다 1점, 총 10점으로 사용합니다.

점검 항목통과 기준점수
파일 3개 존재각 백업 위치에서 직접 확인1
백업 장치 독립성원본과 별도 보관 확인1
복원 경로 확인복원용 폴더를 따로 만들 수 있음1
문서 내용 확인복원본의 실제 본문 확인1
사진·영상 확인첫 부분 외 중간·끝까지 확인1
SHA-256 비교동일 버전 표본 파일 1개 일치1
중요 폴더 점검누락될 가능성이 큰 폴더 확인1
복구 인증 준비계정·키·복구 경로 확보1
삭제·변경 방어별도 버전 또는 독립 사본 존재1
다음 점검 계획기록 날짜와 담당자 정함1

8~10점이라고 전체 복구 성공을 보장하지 않습니다. 특히 테스트하지 않은 파일, 응용프로그램 데이터베이스, 시스템 설정에는 미확인 위험이 남을 수 있습니다. 점수는 스스로 놓친 부분을 파악하는 도구일 뿐입니다.

실험에서 점수가 높더라도 정기적으로 전체 또는 더 넓은 범위를 검증할 필요가 있습니다. NCSC는 백업을 정기적으로 시험해야 한다는 점을 분명히 권고합니다.

16. 일상에서 실행하는 ‘무손실 복원 리허설’ 세 가지

사례 1: 가족 사진

가장 오래된 사진 한 장과 최근 사진 한 장을 선택합니다. 별도 저장소에서 꺼내 새로운 폴더로 복사한 뒤 파일을 열어 확대하고 촬영 날짜를 확인합니다. 이 실험이 성공해도 모든 사진의 복구 가능성이 입증된 것은 아니므로 날짜가 다른 여러 폴더를 순차적으로 검사하는 편이 좋습니다.

사례 2: 업무용 보고서

완료된 보고서 PDF와 원본 편집 파일을 선택합니다. 두 파일을 함께 복원해 PDF는 읽을 수 있는지, 원본 문서는 필요한 편집 앱에서 열리는지 확인합니다. 폰트나 연결 이미지 같은 외부 의존성이 있다면 필요한 자료도 함께 보관돼 있는지 점검합니다.

사례 3: 개인 프로젝트

코드 프로젝트나 디자인 파일 하나를 선택합니다. 프로젝트 파일을 별도 위치에 복원하고 필요한 보조 파일, 템플릿, 환경 설정 파일을 찾습니다. 단순히 파일 한 개만 존재한다고 실행 가능한 프로젝트 전체를 복원했다고 할 수 없습니다.

공통 원칙: 테스트 과정에서 실제 운영 문서와 작업 환경을 덮어쓰지 않습니다. 업무용 데이터는 권한을 가진 사용자만 접근하며, 복원본을 공유 폴더에 무심코 올리지 않도록 주의합니다.

17. 15분 실험 기록 양식: 다음 번에는 같은 실수를 하지 않기

정기 점검은 간단한 기록이 있어야 반복하기 쉽습니다. 다음 표는 그대로 복사해 개인 노트나 스프레드시트에 사용할 수 있습니다.

18. 자주 묻는 질문

Q. 파일을 외장하드에 복사했으면 백업이 끝난 것 아닌가요?

복사본을 만든 것이 첫 단계입니다. 파일이 실제로 열리는지, 원본과 별도로 보관되는지, 다른 위치에 다시 복원할 수 있는지 확인해야 복구 가능성을 판단할 수 있습니다.

Q. 원본을 지우고 외장하드 파일만 남겨야 복원 시험이 되나요?

아닙니다. 원본은 그대로 두고 별도의 복원_시험 폴더에 파일을 꺼내는 방식으로 검증할 수 있습니다. 실제 원본을 지울 필요가 없습니다.

Q. SHA-256이 같으면 백업은 100% 완벽한가요?

아닙니다. 같은 파일의 바이트 내용이 일치한다는 강력한 근거일 뿐입니다. 원본 자체의 손상, 최신 버전 여부, 전체 폴더 누락, 암호와 프로그램 호환성은 따로 점검해야 합니다.

Q. Windows에서 SHA-256을 확인하려면 유료 앱이 필요한가요?

필요하지 않습니다. Microsoft PowerShell의 Get-FileHash로 확인할 수 있습니다. 정확한 원본·복원본 경로를 지정해야 합니다.

Q. Mac에서도 해시 비교를 할 수 있나요?

네. 터미널에서 shasum -a 256을 이용할 수 있습니다. 파일의 실제 경로가 맞는지 확인하고 해시 값을 비교하면 됩니다.

Q. Windows 파일 기록에서 복원하면 지금 쓰는 파일이 덮어써지나요?

기본 복원은 현재 파일을 대체할 수 있습니다. Microsoft는 다른 위치로 복원하는 옵션도 설명하므로, 시험이라면 그 방법을 우선 사용하세요.

Q. Time Machine 복원은 어떻게 안전하게 시험하나요?

Time Machine 복원은 원래 위치로 돌아갈 수 있으므로 실제 업무 파일과 충돌하지 않도록 시험용 파일과 폴더를 미리 준비해 검증하세요. 현재 데이터를 덮어쓰지 않도록 주의해야 합니다.

Q. OneDrive의 파일을 PC에서 지웠는데 웹에서도 사라졌어요.

OneDrive는 동기화 서비스이므로 삭제가 다른 기기 및 클라우드에 반영될 수 있습니다. Microsoft의 OneDrive 웹 휴지통과 버전 기록을 확인하세요. 보존 기간과 계정 정책에 제한이 있습니다.

Q. 가족 사진 수천 장을 15분에 전부 검사할 수 있나요?

아닙니다. 이 실험은 표본 파일 몇 개를 통한 복원 절차 시험입니다. 수천 장의 전수 무결성 검사는 더 긴 시간과 별도 방법이 필요합니다.

Q. 외장하드 한 개와 클라우드 한 개면 충분한가요?

필요한 자료의 중요성, 위험 상황, 백업의 독립성과 복원 가능 여부에 따라 달라집니다. NCSC는 원본을 포함한 세 개의 사본, 서로 다른 매체, 다른 장소 보관이라는 3-2-1 방법을 안내합니다.

19. 백업이 ‘정말 복구되는지’ 최종 체크리스트

  • ☐ 원본을 절대 삭제하지 않고 실험했습니다.
  • ☐ 원본과 실제로 다른 백업 저장 위치를 확인했습니다.
  • ☐ 표본 파일을 적어도 세 가지 유형으로 선택했습니다.
  • ☐ 복원본은 별도 ‘복원_시험’ 폴더에 만들었습니다.
  • ☐ 문서의 마지막 페이지와 사진·동영상의 중간 부분까지 확인했습니다.
  • ☐ 동일 시점의 파일 1개를 SHA-256으로 비교했습니다.
  • ☐ 해시가 같아도 원본 자체가 손상됐을 수 있다는 점을 이해했습니다.
  • ☐ File History나 Time Machine에서 기존 파일을 덮어쓰지 않았습니다.
  • ☐ 클라우드 동기화와 독립적인 백업의 차이를 확인했습니다.
  • ☐ 중요한 폴더가 자동 백업 대상에 포함돼 있는지 확인했습니다.
  • ☐ 암호화 저장소와 클라우드 계정의 복구 경로를 확인했습니다.
  • ☐ 백업 매체 분리, 추가 사본, 오프사이트 보관 여부를 점검했습니다.
  • ☐ 결과와 실패 원인을 기록하고 다음 시험 날짜를 정했습니다.

결론: 백업을 ‘했다고 생각하는 것’과 실제로 복원해 쓸 수 있다는 사실을 확인하는 것은 다릅니다. 중요한 파일 3개만이라도 별도 복원 → 실제 열기 → SHA-256 비교를 진행해 보세요. 이 실험은 전체 시스템의 복구 가능성을 보증하지는 않지만, 단순 복사나 동기화 완료 표시로는 발견하기 어려운 문제를 찾아내는 실용적인 출발점입니다.
