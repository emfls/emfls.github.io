구글은 왜 권한 관리가 이렇게 복잡한가

구글은 현재 200개에 가까운 서비스를 운영하고 있습니다. Gmail, 구글 드라이브, 구글 캘린더, YouTube, 구글 미트… 이 서비스들은 각자 독립된 팀이 운영하지만, 사용자 경험 차원에서 서로 긴밀하게 연동됩니다. Gmail에서 메일 작성 중에 구글 드라이브 파일을 첨부하거나, 구글 캘린더 일정에 미트 회의 링크가 자동으로 삽입되는 것이 대표적인 예입니다.

문제는 바로 이 연동 과정에서 발생합니다. Gmail 팀 개발자가 드라이브 파일을 첨부하는 기능을 만들려면, 구글 드라이브 팀에 연락해 어떤 API를 써야 하는지 물어봐야 합니다. 그리고 그 API를 통해 가져온 파일들이 현재 사용자가 실제로 접근할 권한이 있는지 일일이 확인해야 합니다. 서비스가 몇 개면 모를까, 200개가 넘어가면 이 과정은 기하급수적으로 복잡해집니다.

⚠️ 권한 관리의 세 가지 난관

1. 소유권 확인: 이 문서를 정말 이 사용자가 만든 것인가?

2. 접근 권한 확인: 이 사용자가 이 문서를 읽기·수정할 수 있는가?

3. 그룹 권한: 사용자가 속한 팀이나 그룹에 부여된 권한은?

수백억 개의 데이터가 쌓인 상황에서 이 세 가지를 매번 각 서비스에 직접 물어보는 방식으로는 속도와 일관성을 동시에 확보할 수 없습니다. 구글은 이 문제를 해결하기 위해 Zanzibar라는 전용 시스템을 설계했습니다.

Zanzibar란 무엇인가 — 권한의 단일 진실 공급원

Zanzibar는 구글이 운영하는 모든 서비스에 흩어진 수백억 개의 데이터 권한 정보를 한 곳에 모아 관리하는 초대형 데이터베이스이자 API 시스템입니다. 공식 논문에서는 "글로벌 인가(Authorization) 시스템"이라고 표현합니다.

기존 방식과의 핵심 차이는 이렇습니다. 예전에는 Gmail이 드라이브 파일의 권한을 알고 싶으면 구글 드라이브 서버에 직접 요청을 보내야 했습니다. Zanzibar 이후에는 Gmail이 Zanzibar API 하나만 호출하면 됩니다. 구글 드라이브, YouTube, 캘린더 — 어떤 서비스의 데이터든 권한 정보는 Zanzibar에 다 있기 때문입니다.

💡 핵심 개념: 단일 진실 공급원(Single Source of Truth)

각 서비스가 권한 정보를 따로따로 보관하면, 어떤 서비스는 최신 정보를 갖고 있고 어떤 서비스는 오래된 정보를 갖고 있어 불일치가 생깁니다. Zanzibar는 권한의 "원본"을 한 곳에만 저장해 이 문제를 원천 차단합니다.

이 발상은 매우 단순하지만, 구현은 전혀 단순하지 않습니다. 전 세계 사용자가 동시에 수억 건의 권한 조회를 보내는 상황에서, 10ms 이하의 응답 속도를 유지해야 하기 때문입니다.

릴레이셔널 튜플 — 권한을 저장하는 방식

Zanzibar가 권한을 저장하는 핵심 자료구조는 릴레이셔널 튜플(Relational Tuple)입니다. 형태는 놀라울 만큼 간단합니다.

// 형식: <오브젝트> # <관계> @ <유저> document:readme#owner@user:1 // → 유저 1이 readme 문서의 소유자(owner)다 document:readme#viewer@user:2 // → 유저 2가 readme 문서를 열람(viewer)할 수 있다 document:readme#viewer@group:engineers#member // → engineers 그룹의 멤버들이 readme 문서를 열람할 수 있다 group:engineers#member@user:3 // → 유저 3은 engineers 그룹의 멤버다

이 네 줄의 튜플을 조합하면 다음을 한번에 도출할 수 있습니다. 유저 3은 engineers 그룹의 멤버이고, engineers 그룹 멤버는 readme 문서를 열람할 수 있으므로, 유저 3은 readme 문서를 볼 수 있다는 결론이 나옵니다. 직접적인 권한 부여 없이 그룹을 통한 간접 권한 전파가 가능한 것이 핵심입니다.

관계(relation)의 이름은 개발자가 자유롭게 정의할 수 있습니다. owner, viewer, editor, commenter — 어떤 이름도 가능합니다. 구글 드라이브의 "공유" 기능이 바로 이 튜플을 추가하는 동작입니다.

그래프 탐색으로 권한 확인하기

수백억 개의 튜플이 데이터베이스에 저장되어 있을 때, 특정 사용자가 특정 데이터에 접근할 수 있는지를 어떻게 빠르게 찾아낼까요? Zanzibar는 이 튜플들의 관계를 방향성 그래프(Directed Graph)로 취급합니다.

예를 들어 "유저 3이 readme 문서를 볼 수 있는가?"를 확인하려면, Zanzibar는 readme 문서의 viewer 노드에서 시작해 연결된 엣지를 따라가며 user:3이 나오는지 탐색합니다. 중간에 그룹 노드를 만나면 그 그룹의 멤버 노드로 계속 탐색을 이어갑니다.

조회 유형API 이름동작
권한 확인Check유저가 특정 오브젝트에 대한 권한을 갖고 있는지 True/False 반환
권한 목록Read특정 오브젝트에 접근 가능한 유저/그룹 목록 반환
권한 수정Write튜플 추가·삭제로 권한 변경
일관성 보장Zookie쓰기 직후 읽기 시 최신 데이터 반환 보장 토큰

내부 구현이 복잡하더라도, 구글 내부 개발자들은 Check, Read, Write 세 가지 API만 알면 됩니다. Zanzibar가 그래프 탐색과 캐싱, 분산 처리를 모두 알아서 처리합니다.

전 세계 10ms — 어떻게 가능한가

Zanzibar가 달성한 가장 인상적인 수치는 전 세계 어디서든 10ms 이하의 응답 속도입니다. 서울에서 요청을 보내도, 런던에서 요청을 보내도 동일한 속도를 목표로 합니다. 이것이 가능한 이유는 세 가지입니다.

첫째, 전 세계 데이터 센터 복제입니다. Zanzibar의 데이터베이스와 서비스는 구글이 보유한 전 세계 데이터 센터에 복제되어 있습니다. 사용자의 요청은 지리적으로 가장 가까운 데이터 센터에서 처리됩니다.

둘째, 적극적인 캐싱입니다. 자주 조회되는 권한 정보는 메모리에 캐시해 디스크 읽기를 최소화합니다.

셋째, Spanner 기반 강력한 일관성입니다. 구글의 분산 데이터베이스 Spanner 위에 구축되어, 전 세계 어느 노드에서 읽어도 동일한 데이터를 보장합니다.

✅ 트레이드오프: 업데이트 비용

빠른 조회의 대가로 쓰기 비용이 높습니다. YouTube에 영상을 올리거나 드라이브에 문서를 생성할 때마다 Zanzibar에도 새 튜플을 추가해야 합니다. 권한이 바뀔 때도 마찬가지입니다. 구글은 이 불편함을 감수하고 "조회는 무조건 빠르게"를 선택했습니다.

Zookie — 쓰기 직후 읽기 문제 해결

분산 시스템에서 흔히 발생하는 문제 중 하나가 New Enemy 문제입니다. 권한을 취소(삭제)하는 쓰기 요청을 보낸 직후, 캐시된 이전 데이터를 읽어 "여전히 권한이 있다"고 잘못 판단하는 상황입니다.

Zanzibar는 이를 Zookie라는 토큰으로 해결합니다. 쓰기 요청이 완료되면 Zookie 토큰이 반환됩니다. 이후 Check 요청을 할 때 이 토큰을 함께 전달하면, Zanzibar는 해당 쓰기 이후의 상태를 반드시 반영한 결과를 돌려줍니다. 캐시가 오래되었더라도 Zookie 기준 이후의 데이터로 강제 동기화됩니다.

실제로 구글 드라이브에서 누군가의 공유를 취소한 직후 그 사람이 링크에 접근하면 즉시 거부되는 것, 이 Zookie 메커니즘 덕분입니다.

오픈소스 Zanzibar — 내 서비스에도 도입할 수 있다

구글이 2019년 Zanzibar 논문을 공개한 이후, 이 설계를 바탕으로 한 오픈소스 라이브러리와 서비스들이 다수 등장했습니다. 대표적인 것들을 소개합니다.

이름형태특징
OpenFGA오픈소스 서버Auth0가 만든 Zanzibar 구현체, CNCF 프로젝트
SpiceDB오픈소스 서버Authzed 개발, Go 기반, 클라우드 네이티브
Permify오픈소스 서버Golang 기반, REST·gRPC API 제공
Ory Keto오픈소스 서버경량 구현체, Kubernetes 친화적

직접 서버를 운영하기 어렵다면 Authzed Cloud(SpiceDB 관리형 서비스)나 Auth0 FGA(OpenFGA 관리형 서비스) 같은 SaaS 옵션도 있습니다. 유저가 1억 명을 넘어 권한 관련 코드가 점점 복잡해지고 있다면, 이런 솔루션 도입을 진지하게 검토할 시점입니다.

💡 도입 판단 기준

여러 서비스가 동일한 리소스의 권한을 공유해야 하거나, 그룹·팀 기반의 복잡한 접근 제어가 필요하거나, 권한 조회가 서비스 성능의 병목이 되고 있다면 Zanzibar 계열 솔루션이 유효합니다.

정리 — Zanzibar가 개발자에게 주는 교훈

구글이 Zanzibar로 해결한 문제의 본질은 "복잡성의 한 곳 집중"입니다. 권한 관리라는 복잡한 로직을 전용 시스템 하나에 몰아 넣고, 나머지 200개 서비스는 단순한 API 호출만 하도록 구조를 만든 것입니다.

릴레이셔널 튜플 형태의 자료구조는 놀라울 만큼 단순하지만, 그 단순함이 오히려 수백억 개 규모로도 확장 가능한 일관성을 만들어냅니다. object#relation@user 세 칸이 전부입니다. 구글이 그 세 칸으로 전 세계 서비스의 권한을 10ms에 처리합니다.

스타트업이든 대기업이든, 서비스가 커질수록 권한 로직은 코드 전체에 흩어지기 쉽습니다. 조기에 Zanzibar 계열 접근법으로 권한을 분리해 두면 나중에 수백억 개를 다루는 시스템으로 확장할 때도 구조를 다시 짜는 고통을 피할 수 있습니다.
